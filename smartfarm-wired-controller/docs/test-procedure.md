# 단계별 시험 절차

각 항목은 실물 보드가 있어야 확인 가능합니다(`NEEDS_HARDWARE_TEST`). 실제 결과를 이 표에 채워가며 진행하세요.

## 단계 1: 보드 단독 시험

| 항목 | 기대 결과 | 실제 결과 |
|---|---|---|
| Relay-6CH CH1~CH6 1초 간격 순차 ON/OFF | 릴레이 클릭음/LED로 순서대로 확인 | |
| 릴레이 활성 레벨 확인 | active-high로 추정(문서상) — 실측 확인 | |
| 재부팅 중 릴레이 순간 ON 여부 | 순간적으로도 켜지지 않아야 함 | |
| 메인 보드 W5500 DHCP 연결 | IP 할당받음, 시리얼로 `[ETH] IP: ...` 확인 | |
| 이더넷 케이블 단절/복구 | 단절 시 감지, 재연결 시 자동 복구(재부팅 없이) | |
| **MQTT 계층별 진단 로그** | `[DNS]`→`[TCP]`→`[TLS] handshake success`→`[MQTT] connected` 순서로 성공 로그 확인(`docs/mqtt-topics.md` 참고) | |
| **MQTT clientId 고유성** | 시리얼에서 `[MQTT] clientId: ctlr-0004-eth-XXXXXXXXXXXX` 확인, 기존 WiFi ctlr-0004와 다른 값인지 | |
| **(2026-08-23 추가) MQTT 연결 소요시간** | `[MQTT] 연결 시도 소요시간: Nms` 확인, 3초 이상이면 경고 로그가 뜨는지, RS485 워치독(10초) 대비 여유가 있는지 | |
| **(2026-08-23 추가) rc=-2와 실제 rejected 구분** | 연결 실패 시 `[TLS] handshake/secure transport failed`+`[MQTT] CONNECT not sent`(전송 자체 실패)와 `[MQTT] CONNECT rejected: rc=1~5`(브로커 실제 응답)가 로그상 명확히 구분되는지 | |

## 단계 2: RS485 시험

| 항목 | 기대 결과 | 실제 결과 |
|---|---|---|
| 짧은 선으로 A-A, B-B 연결 | | |
| Master가 Slave 주소 1 폴링 | 정상 응답 | |
| CH1~CH3 ON/OFF 명령 + 읽기 검증 | 명령대로 동작 + 상태 일치 확인 | |
| CRC 오류/응답 타임아웃 시험 | 재시도 후 fault 보고 | |
| RS485 선 분리 → 10초 내 전체 OFF | 팔 노드 자체 워치독 동작 | |
| RS485 재연결 → 상태 재동기화 | 메인이 현재 목표상태 재전송 | |

## 단계 4: 유량계 시험 (2026-08-23 — 팔 노드로 이전됨)

### 4-1. 전기적 확인 (배선 전 필수, `docs/wiring.md` "유량계 배선" 참고)

| 항목 | 기대 결과 | 실제 결과 |
|---|---|---|
| 유량계 실제 공급전압 실측(빨강-검정) | 데이터시트 범위(3.5~24V) 내 | |
| 신호선(노랑) 풀업 전 상태 | 오픈컬렉터라 붕 뜬 상태(불안정) | |
| 절연 입력회로(포토커플러) 단독 벤치 테스트 | **PC817 내부 입력 LED는 적외선이라 육안 확인 불가.** 대신 출력단(2차측, `FLOW_PULSE_PIN` 노드)을 멀티미터/오실로스코프로 측정 — 펄스 없음: 약 3.3V, 펄스 발생: 약 0V. 또는 임시 가시광 테스트 LED(`docs/wiring.md` "PC817 동작 확인 방법" 방법 C, R_test=270Ω@3.3V) 사용. 상세: `docs/wiring.md` "PC817 동작 확인 방법" 절 | |

### 4-2. 팔 노드 측정 확인

| 항목 | 기대 결과 | 실제 결과 |
|---|---|---|
| `FLOW_PULSE_PIN` 물리적 방향 실물 대조 | GPIO4/H1 15번은 공식 회로도로 확정됨(`docs/hardware-verification.md` "2-1"절). 배선 전 H1 커넥터 실크스크린 사진으로 15번 핀 위치가 맞는지만 최종 확인(`config.example.h`에 이미 `#define FLOW_PULSE_PIN 4` 반영됨) | |
| 알려진 주파수(1/10/50/100Hz) 펄스 입력 | `test/flow_pulse_generator` 사용, 팔 노드 시리얼에서 `[FLOW]` 로그 확인 | |
| 순간유량(mL/min), 구간사용량(mL), 누적(mL) | 계산값과 실측 일치 | |
| 주파수별 펄스 누락률 측정 | 낮을수록 좋음, 손실 있으면 대안 검토(`open-decisions.md`) | |
| 글리치 필터(`FLOW_MIN_PULSE_INTERVAL_US`) 동작 | 아주 빠른 노이즈성 토글이 카운트 안 되는지 | |
| 밸브 전부 OFF인데 강제로 펄스 입력 | `FLOW_DIAG_BIT_UNEXPECTED_FLOW` 플래그 세워짐 | |
| 밸브 ON 상태에서 펄스 끊기 | 설정시간(기본 30초) 후 `FLOW_DIAG_BIT_NO_FLOW_TIMEOUT` 플래그 | |
| 재부팅 후 누적값 복원 | NVS에서 복원(팔 노드가 유일한 기준 원장) | |
| `FLOW_TOTAL_ML_SEED` 마이그레이션 | 정의 시 최초 부팅에만 적용, 재부팅 후엔 무시되는지 | |

### 4-3. Modbus 전달 확인

| 항목 | 기대 결과 | 실제 결과 |
|---|---|---|
| 메인 노드가 IR 30008~30022 폴링 | 팔 노드 값과 메인 노드 로그값 일치 | |
| `IR_PROTOCOL_VERSION` 불일치 시뮬레이션 | 팔 노드를 구버전(v1)으로 되돌려 테스트 → 메인이 "미지원"으로 안전 처리, 크래시 없음 | |
| 32/64bit rollover 값 | (실기 불가 시 코드 리뷰로 대체) `getFlowTotalMl()` 등이 unsigned 뺄셈 기반이라 rollover에도 안전한지 확인 | 코드 검토로 확인(아래 "검증" 절) |
| **원자성(seqlock)** | 유량 계산이 한창 진행 중(1초 주기)일 때 Modbus 폴링이 겹쳐도 응답값이 서로 다른 시점 필드가 안 섞이는지 — 실기 부하시험 또는 로그로 `IR_FLOW_SEQ`가 항상 짝수로 관측되는지 | |
| RS485 단절 중 메인 노드 flow1/total | 값이 그대로 멈춰있고(증가 안 함) `rs485/node1/status`가 `timeout`으로 바뀌는지 | |
| 메인/팔 노드 유량 중복누적 없음 | 메인 재부팅해도 flow1/total이 튀지 않는지(메인은 누적을 갖지 않으므로) | |

## 단계 5: 현장 시험 (LED/저전압 부하로 먼저)

`docs/wiring.md`의 "현장 전환 및 롤백 절차"를 따르세요.

| 장애 시나리오 | 기대 결과 | 실제 결과 |
|---|---|---|
| 인터넷 차단 | 로컬 제어/안전기능 계속 | |
| MQTT 서버 차단 | 상동 | |
| Ethernet 케이블 분리 | 상동, 재부팅 없음 | |
| RS485 A/B 분리 | 팔 노드 안전 OFF | |
| 메인 노드 전원 재부팅 | 부팅 시 전부 OFF, 이후 정상 복귀 | |
| 팔 노드 전원 재부팅 | 상동 | |
| 유량계 선 단선 | `flow1/rate`가 0으로, 밸브 ON 중이면 무유량 진단 플래그가 `fault` 토픽으로 발행(있는 척 안 함) | |
| 잘못된 명령 연속 입력 | 무시, 정상 명령엔 계속 응답 | |
| 구역A 로컬재생 (인터넷 3~5분 이상 차단) | 정지상태부터 안전하게 재생 시작, 서버 복귀 시 즉시 서버 우선 | |
| 포깅 중 인터넷 차단 | 포깅은 안전 정지(재생 안 함) | |
