# Modbus RTU 레지스터 맵 (확정)

라이브러리: **eModbus v1.7.4.stable** ([GitHub](https://github.com/eModbus/eModbus)) — ESP32 전용 설계, FreeRTOS 별도 태스크로 통신을 처리해 `loop()`를 막지 않음(작업지시서 11번 "긴 delay/while 금지" 요구사항과 정확히 맞음). Master(`ModbusClientRTU`)와 Slave(`ModbusServerRTU`) 역할을 모두 지원해서 메인/팔 노드에 각각 그대로 사용.

PlatformIO 사용 시 `platformio.ini`에 `lib_ldf_mode = deep+` 추가 필요(이더넷 라이브러리와 함께 쓸 때 빌드 문제 방지, eModbus 공식 문서 권고).

기본 통신 설정: RTU, 9600 baud, 8N1, half-duplex, **하드웨어 자동 방향제어**(RS485 트랜시버가 자동으로 송수신 전환 — DE/RE GPIO 토글 코드 불필요, `docs/hardware-verification.md` 참고).

⚠️ **주의**: 아래 "문서상 주소"는 사람이 읽기 위한 전통적 Modbus 표기(1-base, 0x 계열 접두)이고, **실제 코드(eModbus API)는 0-base 오프셋을 그대로 사용**합니다. 예: "문서상 00001"은 코드에서 `addr = 0`.

## Coils (FC01 읽기 / FC05 단일쓰기 / FC15 다중쓰기) — 릴레이 명령

| 문서상 주소 | 코드상 offset | 기능 | 비고 |
|---:|---:|---|---|
| 00001 | 0 | CH1 메인밸브 ON/OFF | |
| 00002 | 1 | CH2 포깅밸브 ON/OFF | |
| 00003 | 2 | CH3 바이패스밸브 ON/OFF | |
| 00004 | 3 | CH4 예비 | 1차 버전 미사용 |
| 00005 | 4 | CH5 예비 | 1차 버전 미사용, 부트 스트래핑 핀(GPIO45) 주의 |
| 00006 | 5 | CH6 예비 | 1차 버전 미사용, 부트 스트래핑 핀(GPIO46) 주의 |

**멱등성**: 동일 값(예: 이미 ON인데 또 ON)을 반복 write해도 팔 노드는 "상태 변화 없음"으로 처리 — 안전 타임아웃 타이머가 리셋되지 않음(가장 중요한 안전 규칙, `docs/architecture.md` 참고). 타이머는 오직 **OFF→ON 전이**에서만 새로 시작됩니다.

## Input Registers (FC04, 읽기전용) — 팔 노드 → 메인 노드 상태 보고

### 블록 1: 릴레이/시스템 (변경 없음)

| 문서상 주소 | 코드상 offset | 기능 | 비고 |
|---:|---:|---|---|
| 30001 | 0 | 실제 출력 비트마스크 | bit0~bit2 = CH1~CH3 **실측 릴레이 상태**(명령이 아니라 실제 GPIO 레벨 기준) |
| 30002 | 1 | 결함 비트마스크 | bit0~bit2 = CH1~CH3 안전타임아웃 발동, bit8 = 최근 통신 CRC오류 발생 이력 |
| 30003 | 2 | uptime 하위 16bit (초) | |
| 30004 | 3 | uptime 상위 16bit (초) | 30003+30004로 32bit 초단위 uptime 구성 |
| 30005 | 4 | 펌웨어 버전 | major*100+minor (예: 101 = v1.1) |
| 30006 | 5 | 마지막 처리한 명령 시퀀스 번호 | Holding Register 40001에 메인이 쓴 값을 그대로 echo — 메인이 "내 명령이 실제로 처리됐는지" 진단용 |
| 30007 | 6 | **프로토콜(레지스터맵) 버전** | `PROTOCOL_VERSION`(현재 2). 메인 노드가 자신이 아는 값과 비교 — 다르면(특히 팔 노드가 더 낮으면) 유량 블록(30008~)을 신뢰하지 않고 "미지원"으로 안전 처리 |

**"명령 성공 여부 확인" 방식**: 메인 노드는 코일에 쓰기만 하고 끝내지 않습니다. 쓰기 직후(또는 다음 정기 폴링에서) **30001(실제 출력 비트마스크)을 다시 읽어서 원하는 상태와 일치하는지 확인**합니다. 불일치가 지속되면 결함으로 판단해 `tansaeng/ctlr-0004/fault`로 발행합니다.

### 블록 2: 유량계 (v2, 2026-08-23 추가)

값은 팔 노드에서 계산하고, 메인 노드는 읽기만 합니다(단일 기준 원장 = 팔 노드). **워드 순서는 빅엔디안(상위 워드 먼저)**로 통일합니다.

| 문서상 주소 | 코드상 offset | 기능 | 데이터형 | 단위/배율 |
|---:|---:|---|---|---|
| 30008 | 7 | 시퀀스락 패리티 카운터 | uint16 | 홀수=쓰는 중, 짝수=안정. 팔 노드 폴링 주기 대비 정체되면 유량계산 태스크 이상 |
| 30009~30010 | 8~9 | 순간 유량 | uint32 (상위,하위) | mL/min |
| 30011~30012 | 10~11 | 구간 사용량 | uint32 (상위,하위) | mL, 최근 60초 롤링(읽어도 리셋 안 됨 — 폴링 누락에 안전) |
| 30013~30016 | 12~15 | **누적 사용량 (기준 원장)** | uint64 (w0~w3, w0=최상위) | mL |
| 30017~30018 | 16~17 | 마지막 펄스 후 경과시간 | uint32 (상위,하위) | ms |
| 30019 | 18 | 유량 진단 플래그 | uint16 bitmask | 아래 표 |
| 30020 | 19 | 설정된 펄스/L 보정값 | uint16 | 정수(기본 595, config.h에서 변경 가능) |
| 30021~30022 | 20~21 | 원시 누적 펄스카운트 | uint32 (상위,하위) | 진단/디버그 전용 — 롤오버 가능, **기준 원장 아님**(그건 30013~30016) |

**유량 진단 플래그(30019) 비트:**

| 비트 | 이름 | 의미 |
|---:|---|---|
| 0 | `UNEXPECTED_FLOW` | 밸브(CH1~3) 전부 OFF인데 펄스 계속 발생 — 누수/밸브 고장 의심 |
| 1 | `NO_FLOW_TIMEOUT` | 밸브 ON인데 설정시간(기본 30초) 동안 펄스 없음 — 막힘/센서분리 의심 |
| 2 | `SENSOR_FAULT` | 장시간 완전 무신호 등 센서 이상 추정(참고치) |
| 3 | `CONFIG_INVALID` | 펄스/L 등 설정값 비정상(0 등) |

**원자성(찢어진 값 방지)**: eModbus 워커 함수는 FC04 요청 하나당 **하나의 스냅샷**(seqlock으로 보호된 단일 복사)에서 `regs[IR_COUNT]` 배열 전체를 채운 뒤 응답을 만듭니다. 즉 메인 노드가 30008~30022를 한 번의 Modbus 읽기로 가져오면, 그 안의 모든 값은 항상 같은 시점의 일관된 스냅샷입니다(레지스터마다 다른 시점 값이 섞여 들어올 수 없음). 팔 노드 내부에서는 유량 계산 태스크가 스냅샷을 갱신할 때 시퀀스 카운터를 홀수→(필드 갱신)→짝수 순서로 올리고, 읽는 쪽(Modbus 워커)은 시작/끝 시퀀스가 같고 짝수일 때만 유효한 복사로 인정, 아니면 재시도합니다(락 없이 안전하게 동시접근 처리하는 표준 seqlock 기법).

## Holding Registers (FC03 읽기 / FC06,FC16 쓰기) — 메인 노드 → 팔 노드 진단용

| 문서상 주소 | 코드상 offset | 기능 | 비고 |
|---:|---:|---|---|
| 40001 | 0 | 명령 시퀀스 번호 | 메인이 폴링/명령마다 증가시켜 씀. 팔 노드는 그대로 받아서 IR 30006으로 echo만 함(로직에 영향 없음, 순수 진단용) |

## 통신 정책 (작업지시서 5번 요구사항 반영)

- **정상 폴링 주기**: 1초 이내 (코일 읽기로 상태 확인 + 명령 있으면 쓰기)
- **응답 타임아웃**: 200ms, **최대 재시도**: 3회 (연속 실패 시 통신 장애로 판단)
- **CRC 오류/타임아웃/재시도 횟수**: 메인 노드가 카운트해서 `tansaeng/ctlr-0004/rs485/node1/status`, `.../lastSeen`으로 발행
- **재연결 시 재동기화**: RS485가 끊겼다 복구되면, 메인 노드는 자신이 갖고 있는 "현재 목표 상태"(마지막으로 서버에서 받은 명령)를 코일에 다시 씀 — 팔 노드 쪽에서 이걸 어차피 멱등하게 처리하므로 안전
- **여러 팔 노드 확장 대비**: Slave 주소는 `RS485_SLAVE_ADDR_RELAY1 = 1` 형태의 상수로 분리, 향후 `RELAY2 = 2` 등을 추가할 수 있게 배열/맵 구조로 설계
