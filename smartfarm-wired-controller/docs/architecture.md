## 권한(authority) 원칙 — 가장 중요한 설계 규칙

이 프로젝트 전체를 관통하는 단일 원칙입니다:

> **서버(데몬)가 살아있는 동안은 서버가 유일한 판단 주체다. ESP32는 어느 쪽도 "서버와 다른 자기 의견"을 갖지 않는다.**

- 메인 노드: 평상시 서버 cmd를 그대로 실행하는 순수 실행기. 구역A 로컬재생조차 "확정 오프라인" 상태에서만, 그것도 서버가 마지막으로 알려준 값 그대로만 사용 — 자체 판단을 만들지 않음.
- 팔 노드: RS485로 받은 코일 값을 그대로 릴레이에 반영. 유일한 "자체 판단"은 안전타임아웃(물리적 안전을 위한 최후 방어선)뿐.

이렇게 설계한 이유는 `ctlr-heat-001`에서 ESP32 자체 AUTO 판단이 서버 명령을 무시해 오작동한 실제 사고 때문입니다(`docs/open-decisions.md` 1번 참고).

## 계층별 실패 대응

| 실패 상황 | 영향 범위 | 대응 |
|---|---|---|
| 인터넷/HiveMQ 장애 | 메인 노드가 서버 명령 못 받음 | RS485/유량측정/안전기능 계속 동작. 구역A만 확정 오프라인(3~5분) 후 로컬재생, 포깅은 정지 |
| Ethernet 케이블 분리 | 상동 | 상동 + 재연결 시 자동 복구, 재부팅 없음 |
| RS485 A/B 분리 | 팔 노드가 메인 명령 못 받음 | 팔 노드 자체 통신워치독(10초)으로 위험출력 자동 OFF |
| 메인 노드 재부팅 | 일시적 제어 공백 | 부팅 시 전부 OFF, 재연결 후 서버에 현재상태 재발행 |
| 팔 노드 재부팅 | 밸브 즉시 OFF | 부팅 시 전부 OFF, 메인 노드가 재동기화 |
| 밸브 개별 안전타임아웃 초과 | 해당 밸브만 | 팔 노드가 독립적으로 강제 CLOSE + fault 보고 |

## 소프트웨어 구조 원칙

- `millis()` 기반 상태머신만 사용, 블로킹 `while`/`delay`/재연결 루프 금지(작업지시서 11번)
- Ethernet / MQTT / RS485 / 유량계 / 로컬재생 / 안전 로직을 별도 모듈(.h/.cpp)로 분리
- 상태가 실제로 바뀔 때만 릴레이 조작 및 MQTT 발행(불필요한 트래픽/EEPROM 마모 방지)
- 명령(의도)과 실제 상태(결과)를 항상 구분해서 다룸 — "명령을 보냈다"와 "실제로 그렇게 됐다"는 다른 것
